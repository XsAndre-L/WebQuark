# WebQuark Component Audit — Fix Backlog

> Generated 2026-07-07 from a full-library code audit: 25 components, 262 component-level findings + 34 cross-cutting patterns (296 total). This is the executor-facing counterpart to the interactive report — every finding, grouped by how safe it is to act on without a human decision first.

## How to use this document

1. **Section A must be confirmed by a human before any of it is implemented.** These change or remove part of the public API surface that AllThings (the downstream consumer) may already depend on.
2. Section B is safe from an API-compatibility standpoint but is large in scope — do these deliberately, one component per commit, not as one sweeping change.
3. Sections C and D are safe to implement autonomously, in any order. Work component-by-component so each change stays reviewable.
4. **Verification command for this repo is Stencil/Vitest, not the Next.js one used elsewhere in this workspace:** run `bun run build` and `bun test` from the WebQuark root after each component's fixes. Use `bun start` (playground at localhost:3333) to eyeball anything visual.
5. Checkboxes track progress — check one off only once the fix has landed and verified, not before.
6. Don't invent scope beyond what's listed here. If something looks wrong or you're unsure a finding still applies, flag it back rather than guessing.

## Section A — 🔴 Sign-off required before implementing

These change or remove something a consumer may already depend on. Confirm each one individually before touching the code.

- [ ] 🔴 BREAKING **Two unrelated components each independently invented a 'two @Props for one concept, reconciled by a getter/@Watch' pattern instead of a single canonical prop — q-link's href/url and q-syntax-box's code/value.**
  - _Affects:_ q-link, q-syntax-box
  - _Why:_ A consumer like AllThings has to learn, per component, which of two same-purpose props is 'the real one' and whether setting both is safe — q-link resolves via an href→url→mailto→tel precedence getter, while q-syntax-box uses paired @Watch handlers that write each prop's value back into the other. Neither pattern is documented as intentional (both ship with zero JSDoc on the affected props), so a consumer can't tell from the API surface alone whether `url` on q-link or `value` on q-syntax-box is a deprecated alias, a synonym, or has subtly different semantics — and the two components don't even agree with each other on which pattern to use for reconciliation (getter vs. bidirectional @Watch).
  - _Recommendation:_ Standardize on exactly one prop name per concept and remove the alias: `href` for navigable-URL components (matching q-button, which already exposes only `href`, not a `href`/`url` pair), and `value` for editable-content components (matching q-input/q-textarea's existing `value` convention). A single canonical name per concept is strictly better than either reconciliation strategy because it removes the ambiguity entirely rather than managing it — there is nothing for two props to drift out of sync on if there is only one prop.
- [ ] 🔴 BREAKING **The three form-associated field components most likely to be used interchangeably in the same form — q-input, q-textarea, q-toggle — implement three subtly different 'error state' APIs.**
  - _Affects:_ q-input, q-textarea, q-toggle
  - _Why:_ q-input and q-textarea both declare `@Prop({reflect:true}) error?: string` plus a separate `@Prop() errorMessage?: string`, computing `hasError = !!(error || errorMessage)` and displaying whichever is set — so `error` doubles as a reflected boolean-ish CSS/ARIA hook while `errorMessage` is the real text. q-toggle instead has only `@Prop() error?: string` (confirmed not reflected in toggle.tsx:24), which it renders directly as the message text with no separate flag and no host-attribute reflection. A consumer building one form with q-input, q-textarea, and q-toggle side by side has to write two different error-wiring code paths for what is conceptually the identical concern, and CSS/ARIA that keys off a reflected `error` attribute on inputs and textareas silently does nothing on toggles.
  - _Recommendation:_ Standardize the whole 'Unified Form Field' family (q-input, q-textarea, q-toggle, and ideally q-dropdown/q-quantity-selector too) on the input/textarea shape: a reflected boolean-or-flag `error` prop plus a dedicated `errorMessage` string prop. That shape is the only one of the two in use that supports both a CSS/ARIA-hookable reflected state _and_ an independent display string simultaneously — q-toggle's single-prop version can't represent 'in an error state but no message yet' or let external CSS select on error state via `:host([error])` the way its two siblings already do.
- [ ] 🔴 BREAKING **q-card's `elevation` prop accepts two parallel vocabularies for the same three levels ('low'|'medium'|'high' AND 1|2|3), which no other size/variant-style prop in the library does.**
  - _Affects:_ q-card
  - _Why:_ QCardElevation = `'low' | 'medium' | 'high' | 1 | 2 | 3` is a bespoke equivalence table that exists nowhere else in the 24-component surface — QButtonSize, QDropdownSize, QToggleSize, etc. all use exactly one vocabulary (named strings) for their tiers. This forces card.css to duplicate every elevation selector (`.elevation-low, .elevation-1 { ... }`), forces the generated readme.md to expose a confusing six-member union to consumers, and gives AllThings two equally-valid-looking ways to write the same intent with no guidance on which is preferred.
  - _Recommendation:_ Drop the numeric aliases and keep only the named-string vocabulary ('low'|'medium'|'high'), matching how every other tiered prop in the library is expressed. This removes a component-specific, undocumented equivalence table without losing any expressiveness, since the numeric values map 1:1 onto names that already exist.
- [x] 🔴 BREAKING **q-dialog defaults to `backdrop-filter: blur(...)` and is the only place in the entire 24-component library where backdrop-filter appears at all — a direct, isolated breach of the house 'no backdrop-filter anywhere' rule.**
  - _Affects:_ q-dialog
  - _Why:_ This is the single most severe finding in the audit because the rule it breaks isn't a style preference, it's a platform-safety constraint: backdrop-filter is documented to crash/misrender in CEF's offscreen-rendering (OSR) path and Unreal Engine's Webview, which is the entire reason the rest of the library (q-card's explicit 'Glassmorphism support without backdrop-filter to prevent OSR crashes' comment, q-dialog's own effect-solid/effect-none variants, the --q-bg-glass translucent-but-opaque token) goes out of its way to fake glass without it. Because `backdropEffect` defaults to `'blur'`, every consumer who instantiates a q-dialog without explicitly overriding the prop ships the unsafe path by default — the safety property only holds if you know to opt out.
  - _Recommendation:_ Delete the `blur` backdrop effect (and the now-dead --q-dialog-backdrop-filter / --q-glass-blur tokens it consumes) entirely, change the default `backdropEffect` to `'solid'`, and add a lint/CI grep for the literal string `backdrop-filter` across src/components so a future PR can't reintroduce it silently.
- [ ] 🔴 BREAKING **The component exposes two functionally-identical content props, `code` and `value`, each with its own @Watch handler (watchCode/watchValue) that writes back into the other, plus componentWillLoad logic to reconcile whichever one was set initially.**
  - _Affects:_ q-syntax-box
  - _Why:_ This doubles the API surface and cognitive load for consumers ('do I bind to `code` or `value`?') and creates a fragile bidirectional-sync setup: watchCode calls `this.value = finalCode` which will itself trigger watchValue, which computes `finalVal` and calls `this.code = finalVal` again — safe today only because of the `if (this.value !== finalCode)` / `if (this.code !== finalVal)` guards, but any future edit that weakens those guards (e.g. adding transformation logic before the equality check) reintroduces an infinite watch loop. It's undocumented anywhere why both exist (likely `value` for form-association naming conventions vs `code` for domain naming), which compounds the missing-JSDoc finding above.
  - _Recommendation:_ Pick one canonical prop (likely keep `code` as the domain name) and make `value` a getter-only alias documented as 'form-association alias for `code` — do not set both', or collapse to a single prop and expose `value` only via `internals`/form APIs rather than as a second mutable @Prop with its own watcher.
- [ ] 🔴 BREAKING **The component's CSS invents its own --q-quantity-selector-bg/-border-color/-radius/-input-bg namespace instead of building on the library's shared 'Unified Form Field' tokens.**
  - _Affects:_ q-quantity-selector
  - _Why:_ global.css lines 139-156 define --q-field-bg/-border/-radius/-padding specifically so q-input, q-textarea, and q-dropdown share one theming surface. quantity-selector.css lines 6-13 instead re-derives the same concepts from raw --q-bg-surface-2/--q-border-color/--q-radius-md/--q-bg-base with its own hardcoded hex fallbacks, so a consumer restyling 'form fields' library-wide has to separately override this component too.
  - _Recommendation:_ Base `--q-quantity-selector-bg` on `var(--q-field-bg, ...)`, `--q-quantity-selector-border-color` on the field border color, and `--q-quantity-selector-radius` on `var(--q-field-radius, ...)`, the way q-dropdown maps its tokens (global.css lines 152-156).
- [ ] 🔴 BREAKING **q-textarea has no `size` prop, while its sibling form fields q-input (input.tsx line 24, `size: QInputSize = 'md'`) and q-dropdown (`size: QDropdownSize = 'md'`) both expose one with matching `.size-sm/md/lg` CSS scale classes.**
  - _Affects:_ q-textarea
  - _Why:_ Forms that mix q-input and q-textarea (a very common combination) cannot apply a consistent visual density across fields, breaking the 'Unified Form Field' token intent already established in global.css (--q-field-\* tokens exist specifically to keep q-input/q-textarea aligned).
  - _Recommendation:_ Add `@Prop({ reflect: true }) size: QTextareaSize = 'md';` (new type in textarea.types.ts) and mirror input.css's `.input-wrapper.size-sm/.size-md/.size-lg` blocks as `.textarea-wrapper.size-sm .textarea-box { padding: 6px 10px; font-size: var(--q-font-size-sm, 0.7rem); }` etc.
- [x] 🔴 BREAKING **Component ships backdrop-filter (blur) as its DEFAULT backdrop effect, directly violating the house rule that no component may use backdrop-filter for CEF/Unreal Webview safety.**
  - _Affects:_ q-dialog
  - _Why:_ dialog.tsx:24 declares `@Prop({attribute:'backdrop-effect', reflect:true}) backdropEffect: QDialogBackdropEffect = 'blur'`, and dialog.css:39-41 wires `.effect-blur { backdrop-filter: var(--q-dialog-backdrop-filter, blur(var(--q-glass-blur, 12px))); }`. getResolvedBackdropEffect() (dialog.tsx:145-153) even falls back to 'blur' for unrecognized values — the least-safe option, not a safe one. The test suite's own comment ('supports the solid backdrop effect for Unreal-safe rendering', test/dialog.spec.ts:29) proves the authors knew blur is unsafe, yet left it as the out-of-the-box default. Any consumer who instantiates <q-dialog> without explicitly setting backdrop-effect="solid" ships a backdrop-filter into a CEF/Unreal webview, exactly what the rule exists to prevent. The unsafe token even lives in global.css:29-32 (--q-dialog-backdrop-filter), so this isn't a local slip — it's baked into the shared design tokens.
  - _Recommendation:_ Flip the default to the safe option: `@Prop({attribute:'backdrop-effect', reflect:true}) backdropEffect: QDialogBackdropEffect = 'solid';` and change the invalid-value fallback in getResolvedBackdropEffect() to return 'solid' instead of 'blur'. If 'blur' must stay available for non-Unreal web contexts, add a JSDoc warning on the prop ('blur uses backdrop-filter — do not use in CEF/Unreal Engine Webview contexts') so the readme generator surfaces the risk to consumers.

## Section B — 🟡 Judgment calls (safe, but large in scope)

Not breaking, but touch many files or establish a new shared pattern — worth a deliberate, incremental pass rather than one sweeping commit.

- [ ] 🟡 JUDGMENT CALL **The numbered section-header comment system ([1] STENCIL API … [6] RENDER) is applied at three different levels of rigor across the library: fully absent, present-but-misordered, and correctly ordered — with only one component doing it right end to end.**
  - _Affects:_ q-link, q-syntax-box, q-form, q-navbar, q-panel, q-button, q-data-table, q-dropdown, q-quantity-selector, q-card, q-scrollable, q-sidepanel, q-reel, q-toggle, q-step-diagram, q-circular-progress, q-textarea
  - _Why:_ This is meant to be the library's shared 'map' for navigating any component's source. Five components (link, syntax-box, form, navbar, panel) have zero headers, eleven more have the headers but misplace fields/lifecycle hooks/watchers relative to them (e.g. @State declared under section [1] instead of [2], @Watch under [1] instead of [3], business logic inside the '[6] RENDER (Visual Template Only)' section), and only q-textarea implements all six in the documented order with nothing misplaced. A maintainer moving between q-\* files gets a different navigational contract every time, which defeats the entire point of a shared convention in a design-system library — new contributors can't learn one layout and apply it everywhere, and code review can't cheaply check 'is this in the right section' because there's no consistent baseline.
  - _Recommendation:_ Adopt textarea.tsx (C:/Dev/PurelyIT/WebQuark/src/components/inputs/textarea/textarea.tsx) verbatim as the canonical template — it is the only component in the audit set with all six headers present, correctly ordered, and with every field/method/hook actually living in the section its header names. Retrofit the other 16 components against it rather than inventing a new arrangement; that also gives you a single component to point new contributors at.
- [ ] 🟡 JUDGMENT CALL **Every component implementing a 'list of selectable items' widget invents its own ARIA composite-widget pattern, and only one of the four gets it right.**
  - _Affects:_ q-dropdown, q-sidepanel, q-carousel, q-navbar
  - _Why:_ Verified via source: q-dropdown implements a correct roving-tabindex listbox — `role="listbox"` (dropdown.tsx:390), `role="option"` on items (dropdown.tsx:419), and `aria-controls` linking the trigger to the menu (dropdown.tsx:373) — plus full Arrow/Home/End/Enter/Escape keyboard handling. q-sidepanel instead puts `role="menu"` on its nav body (sidepanel.tsx:211) but mixes `role="button"` for groups and `role="menuitem"` for leaves as children of that menu, which is an invalid ARIA menu structure. q-carousel uses `role="tablist"`/`role="tab"` for its indicator dots (carousel.tsx:369,376) with no associated `role="tabpanel"` or `aria-controls` linking a dot to its slide. q-navbar's mobile menu has no ARIA role wiring, no `aria-controls` between the toggle button and the panel, and no Escape/outside-click dismissal at all. Four components solving the same 'set of selectable/navigable items' problem land at four different levels of correctness with no shared reference — a screen-reader user gets a materially different (and in three of four cases broken) experience depending on which component they hit.
  - _Recommendation:_ Treat q-dropdown's listbox/option + aria-controls implementation as the house reference pattern; retrofit q-sidepanel's nav (drop role="button"/role="menuitem" mixing for a valid composition, e.g. plain nav links or a proper menu/menuitem tree), add role="tabpanel"/aria-controls wiring to q-carousel's indicators, and add aria-controls plus Escape/outside-click handling to q-navbar's mobile menu — ideally by factoring the shared keyboard-navigation logic q-dropdown already has into src/utils so the other three consume it instead of re-deriving it.
- [ ] 🟡 JUDGMENT CALL **Meaningful vs. decorative icon/label accessibility is handled with no consistent convention across five components — some meaningful icons get no accessible text, one decorative icon is wrongly exposed.**
  - _Affects:_ q-button, q-link, q-circular-progress, q-thumbnail, q-step-diagram-item
  - _Why:_ q-button has no aria-label prop or mechanism for icon-only buttons, and because of Shadow DOM a consumer's `aria-label` on the host `<q-button>` never reaches the inner `<button>`/`<a>`. q-link's external-link SVG is `aria-hidden` with no accompanying visible/visually-hidden text explaining 'opens in a new tab'. q-circular-progress's custom `label` prop overrides the visible text but is never exposed via `aria-valuetext`, so screen readers only hear the raw percentage. Conversely, q-thumbnail's decorative play-triangle SVG is NOT `aria-hidden`, so it gets redundantly announced. q-step-diagram-item's `.step-badge` is `aria-hidden="true"` yet is independently clickable, creating a keyboard-unreachable hidden activation target. Each of these is the same underlying problem — 'is this icon/graphic meaningful (needs a text alternative) or decorative (needs aria-hidden), and is the interactive control's accessible name actually wired up' — solved differently (or not at all) in five separate files, so fixing one doesn't fix the others and no component can be pointed to as the correct template.
  - _Recommendation:_ Establish one house convention (and ideally a small icon-a11y guideline/util) that: (1) every icon-only interactive control exposes an explicit `label`/`aria-label` prop applied to the inner focusable element, not just the host; (2) every purely decorative icon gets `aria-hidden="true"` unconditionally; (3) props like q-circular-progress's `label` that override visible text also drive `aria-valuetext`/`aria-label`. Apply it to q-button, q-link, q-circular-progress, q-thumbnail, and q-step-diagram-item.

## Section C — 🟢 Library-wide patterns, safe to fix autonomously

Cross-cutting findings not already listed in A or B above.

### Cross-component structural/API consistency (WebQuark 24-component audit)

- [ ] 🟢 SAFE **`@Element() el!: HTMLElement` is declared in 19 of the 24 components as apparent boilerplate, but 5 of those never reference `this.el` anywhere, one component omits the `!` assertion that every other component uses, and one re-guards against a value its own type declares can never be null.**
  - _Affects:_ q-data-table, q-input, q-textarea, q-dialog, q-sidepanel, q-tooltip, q-button
  - _Why:_ An unused `@Element()` is dead code that every future reader has to mentally rule out as 'maybe used somewhere.' Worse, the inconsistent typing (`el!: HTMLElement` vs. tooltip's plain `el: HTMLElement`) and button.tsx's `if (!this.el) return` right after asserting `el!` is never null are two different, contradictory beliefs about whether Stencil guarantees the element reference in this codebase — code following one file as a template will get the wrong mental model depending on which file it copies.
  - _Recommendation:_ Only declare `@Element()` when the class body actually reads `this.el`; delete it from q-data-table, q-input, q-textarea, q-dialog, and q-sidepanel. Where it is declared, always type it `el!: HTMLElement` (matching Stencil's real guarantee that the element is defined once the class is instantiated) and drop redundant `if (!this.el)` guards like button.tsx's — asserting `!` and then re-checking for null in the same class is worse than either picking the assertion (and trusting it) or dropping it (and guarding), because it signals to readers that the codebase itself doesn't trust its own type annotations.
- [ ] 🟢 SAFE **Several props that visibly drive host-level CSS/attribute state are left un-reflected while a directly comparable sibling prop in the same component (or the same conceptual slot in a related component) is reflected — forcing manual, error-prone host-attribute mirroring instead.**
  - _Affects:_ q-tooltip, q-circular-progress, q-carousel, q-step-diagram, q-step-diagram-item
  - _Why:_ q-tooltip declares `position` as a plain @Prop (tooltip.tsx:23) but then hand-writes `position={this.position}` onto the Host in render() (tooltip.tsx:208) purely to reproduce what `reflect:true` gives for free — a duplicated, easy-to-drift source of truth. q-circular-progress reflects `size` but not `indeterminate`, even though `.is-indeterminate` is a real CSS-relevant state (circular-progress.tsx:14-15). q-carousel's `itemWidth` isn't reflected while its sibling booleans (snapAlignment, showArrows, showIndicators, repeat) all are. q-step-diagram's parent doesn't reflect `layout` while its own child, q-step-diagram-item, does reflect the analogous prop — so the exact same concept is handled two different ways one level apart in the same feature. Consumers styling these components from outside the shadow root (a common AllThings pattern for design-system elements) get an inconsistent, undocumented answer to 'can I select on this via a host attribute?' that differs component-by-component with no visible logic.
  - _Recommendation:_ Make `@Prop({reflect:true})` mandatory for any prop whose value needs to be visible as a host DOM attribute for CSS selection or external inspection — never hand-roll the mirroring in render() the way q-tooltip does. This is strictly fewer lines, eliminates an entire class of drift bugs (mirrored value forgotten on one render path), and is already what the majority of the library's reflected props do correctly; q-tooltip's manual approach is the outlier, not a viable second convention.
- [ ] 🟢 SAFE **The house rule that DOM-event-bound private methods are named handleX is inconsistently enforced — including within single files that use both conventions side by side.**
  - _Affects:_ q-data-table, q-navbar, q-step-diagram, q-icon, q-thumbnail, q-panel
  - _Why:_ q-data-table's own class declares both correctly-named `handleRowClick`/`handleRowKeyDown` and incorrectly-named `toggleRowSelection`/`toggleAllSelection` bound directly to `onChange` — proving the convention is known in that very file yet abandoned for adjacent handlers. q-navbar's mobile-menu handlers (`toggleMenu`, `closeMenu`) never use handleX at all. q-step-diagram's `handleLayoutChange` is missing the `private` modifier every other handleX method in the file carries. q-icon and q-thumbnail bind inline arrow functions directly in JSX instead of naming a handleX method at all. Grepping a component for 'how does it respond to clicks/changes/slot updates' is supposed to be answerable by searching for `handle`, but that search silently misses real event wiring in at least six components — which is exactly the kind of cross-file unpredictability a naming convention exists to prevent.
  - _Recommendation:_ Enforce handleX purely by 'what DOM event this method is bound to' (handleClick, handleChange, handleKeyDown, handleSlotchange, handleError), never by what the method does internally (toggle, check, close) — that is the only naming axis that stays consistent regardless of a handler's implementation, and it is already the majority convention; a lint rule flagging any `on*={this.foo}` JSX binding where `foo` isn't inline-arrow or doesn't start with `handle` would catch all six instances mechanically.
- [ ] 🟢 SAFE **The `!` definite-assignment assertion on `@Event()` field declarations is applied to roughly three-quarters of event emitters across the library but omitted on the rest, with no discernible reason for the split.**
  - _Affects:_ q-step-diagram-item, q-thumbnail, q-quantity-selector, q-reel
  - _Why:_ Confirmed by source: `@Event() qChange!: EventEmitter<string>` (with `!`) is the pattern in q-input, q-toggle, q-dropdown, q-data-table, q-link, q-chip, q-sidepanel, q-syntax-box, and q-dialog (30+ occurrences), while q-step-diagram-item's `qItemClick`, q-thumbnail's `qMaximize`, all four of q-quantity-selector's events, and both of q-reel's events omit it. TypeScript treats these identically at runtime (Stencil always assigns the emitter), so the split is purely stylistic — but a stylistic split this close to universal reads as carelessness rather than a deliberate distinction, and it's the kind of tiny inconsistency that erodes confidence that other, more consequential conventions (like `reflect: true` placement) were applied deliberately either.
  - _Recommendation:_ Standardize on always including `!` on `@Event()` fields, matching the supermajority pattern already in use — it correctly documents that Stencil guarantees the emitter is assigned before use, consistent with how `@Element() el!: HTMLElement` is typed elsewhere in the same codebase.
- [ ] 🟢 SAFE **q-icon types every one of its props (`QIconName`, `QIconLibrary`, `QIconSize`, `QIconColor`, `QIconLocalPath`) as a plain `string`, breaking the union-literal-type-alias pattern every other enum-like prop in the library uses.**
  - _Affects:_ q-icon
  - _Why:_ Every other constrained-choice prop in the audited components — QButtonVariant, QLinkVariant, QDropdownSize, QCardElevation, QTooltipPosition, QCarouselSnapAlignment, QToggleType, and more — is declared as a dedicated union-literal type alias, giving IDE autocomplete and compile-time typo-catching to consumers like AllThings. q-icon's `lib` accepts a known small set of keywords ('lucide' | 'font-awesome'/'fontawesome' | 'local' | a custom URL) and `size` accepts a known small set ('sm'|'md'|'lg' plus raw CSS sizes) per its own documented behavior, yet both are typed as unconstrained `string` in icon.types.ts — so a consumer gets zero autocomplete for the documented keyword set and no compiler warning for a typo like `lib="lucid"`, unlike every sibling component's enum-style prop.
  - _Recommendation:_ Type these as `'sm' | 'md' | 'lg' | string` (and the equivalent open union for `lib`) — the `| string` escape hatch preserves the documented flexibility (raw CSS sizes, custom base URLs) while restoring the autocomplete/typo-catching parity every other component in the library already provides for its keyword-like props.
- [ ] 🟢 SAFE **Two test files exercise real shadow-DOM/browser behavior (compiled dist/loader, document.createElement + dispatchEvent) but are named `*.spec.ts` — the house convention reserved for jsdom-style unit tests — instead of `*.cmp.test.ts`.**
  - _Affects:_ q-syntax-box, q-quantity-selector
  - _Why:_ The project's own naming convention (`*.spec.ts` = unit, `*.cmp.test.ts` = browser/Playwright) almost certainly maps to different test-runner configuration or CI stage. A browser-driving test misfiled as `*.spec.ts` risks silently running under a jsdom-based unit runner it isn't actually designed for (or being excluded from whatever suite is scoped by the `.cmp.test.ts` glob), which is a correctness risk for CI, not just a cosmetic naming nit — and it means grepping for 'the browser tests' by filename pattern misses two real ones.
  - _Recommendation:_ Rename `test/syntax-box.spec.ts` and the q-quantity-selector test file to `*.cmp.test.ts` to match their actual execution model, and treat 'does this test touch a compiled bundle / real DOM events, or run against isolated logic' as the deciding factor for the filename — not what the test happens to be called today.
- [ ] 🟢 SAFE **Public `@Method()` APIs across the library are treated as a lower documentation/test bar than `@Prop`/`@Event`, even though methods are the one part of the public surface TypeScript can't help a consumer use correctly.**
  - _Affects:_ q-form, q-dialog, q-carousel, q-scrollable, q-syntax-box
  - _Why:_ q-form's getValues/setValues/resetForm/submitForm, q-dialog's show/close/confirm/cancel, q-carousel's slideTo/updateLimits, q-scrollable's scrollToBottom/scrollToPosition, and q-syntax-box's scrollToBottom are all imperative APIs with no prop-driven equivalent — for q-dialog specifically, `show()`/`close()` are the _only_ way to open/close it programmatically. None of these carry a JSDoc comment (so readme.md's Methods table is blank for all of them), and only a minority have any test invoking them. Because `@Method()` calls are resolved dynamically off a queried custom element rather than shape-checked at the JSX call site the way a `@Prop` is, an undocumented, untested method is the single riskiest part of the public API for AllThings to depend on correctly — there is no compiler or generated-docs safety net at all if the implementation's behavior silently drifts.
  - _Recommendation:_ Require a JSDoc description (what it does, parameter meaning, return-value meaning) and at least one direct test invocation for every `@Method()` as a stricter, non-negotiable minimum bar than what's applied to `@Prop`/`@Event` — since props and events at least get partial safety from TypeScript's structural typing and the generated readme tables, while methods get none of that without their own test coverage.

### WebQuark cross-component consistency: design tokens, class naming, theming, transitions, CEF-safety

- [ ] 🟢 SAFE **Fallback literals baked into `var(--q-token, fallback)` chains for the four most-used shared tokens (--q-font-weight-bold, --q-font-size-base, --q-font-size-lg, --q-radius-lg, --q-padding-lg) are wrong in the majority of components and disagree with each other in 2-3 different ways per token.**
  - _Affects:_ q-card, q-data-table, q-dropdown, q-input, q-textarea, q-reel, q-step-diagram-item, q-circular-progress, q-toggle, q-sidepanel, q-navbar, q-form, q-syntax-box

  - _Why:_ q-input's handleIncrement/handleDecrement duplicate ~15 lines of base-value resolution and clamping almost verbatim within the same file (differing only in +/- and clamp order), and q-quantity-selector implements the same responsibility again from scratch in a separate file. The two implementations have diverged in quality: quantity-selector consistently guards bounds with `!== undefined && !== null` (avoiding the classic min=0/max=0 falsy bug) while its own watchValue guard elsewhere still misses a NaN check, and there's no single place either fix propagates from. Any future numeric-field component (a slider, a stepper) will likely reimplement this a third time.
  - _Recommendation:_ Extract a shared `clampNumeric(value, { min, max, step })` helper into src/utils (covering NaN handling and the min/max!==undefined&&!==null guard pattern already proven in q-quantity-selector) and have both q-input's spinner handlers and q-quantity-selector's increment/decrement/reconcileValue call it.
- [ ] 🟢 SAFE **Two components render the same 'anchor-or-button with a disabled/busy state' responsibility with very different thoroughness — q-link's disabled handling is defense-in-depth, q-button's aria-busy silently skips the anchor branch.**
  - _Affects:_ q-button, q-link
  - _Why:_ q-link strips href/target/rel/download from the DOM when disabled (not just visual styling), sets tabindex=-1 and aria-disabled, adds CSS pointer-events:none, and still guards defensively in the click handler — a genuinely thorough, multi-layered pattern. q-button, which renders the conceptually identical 'this control can be an <a> or a <button>' choice, only sets `aria-busy` on the rendered `<button>` branch (button.tsx:130) and never on the `<a>` branch (button.tsx:108-119) even though `isBtnDisabled`/`loading` apply equally to both. Two components with the same architectural split (dual anchor/button rendering) have diverged on how completely they communicate disabled/busy state to assistive tech, and neither documents which pattern is canonical for the next component that needs this split.
  - _Recommendation:_ Port q-link's disabled-state thoroughness pattern to q-button's `<a>` branch (add aria-busy, and consider stripping href/target/rel/download the same way q-link does when isBtnDisabled is true), and consider documenting the anchor/button dual-render + disabled-state pattern as a reusable reference (or shared render helper) given it will likely recur in future components.
- [ ] 🟢 SAFE **Two components exposing near-identical numeric stepper buttons (+/- controls) give them different accessibility treatment.**
  - _Affects:_ q-input, q-quantity-selector
  - _Why:_ q-input's numeric spinner increment/decrement buttons have `tabindex="-1"` and no `aria-label`, making them keyboard-unreachable and unlabeled for screen readers. q-quantity-selector's equivalent +/- buttons are given `aria-label` and left focusable. Both components are solving the same UI problem (increment/decrement a bounded number) in the same library, yet only one is accessible via keyboard/screen reader — and neither wires ARIA `spinbutton` role or Arrow-key support onto the actual numeric input/display, so even the 'better' of the two is still incomplete.
  - _Recommendation:_ Bring q-input's spinner buttons up to q-quantity-selector's standard (remove tabindex="-1", add aria-label), and add `role="spinbutton"` with `aria-valuenow`/`aria-valuemin`/`aria-valuemax` plus ArrowUp/ArrowDown keyboard support to both components' numeric controls consistently, ideally as a shared internals helper.
- [ ] 🟢 SAFE **Modal/overlay content is linked to its accessible name/description inconsistently: the general-purpose q-dialog and q-tooltip both skip aria-labelledby/aria-describedby wiring that the more specialized q-reel lightbox gets right.**
  - _Affects:_ q-dialog, q-tooltip, q-reel
  - _Why:_ q-reel's lightbox overlay is praised as a genuinely thorough, reusable a11y template: role="dialog", aria-modal, a computed aria-label, full focus-trap and Escape handling. By contrast q-dialog — the library's primary, general-purpose modal component — has role="dialog" and aria-modal="true" but never wires aria-labelledby (to its title) or aria-describedby (to its message/body content), so screen reader users get a generic 'dialog' announcement instead of its actual title/content. q-tooltip has the analogous gap from the other direction: its trigger element has no aria-describedby pointing at the tooltip bubble's id, and the tooltip's own aria-hidden is hardcoded to "true" and never toggles with actual visibility. Three components solving 'associate a floating/overlay region with its trigger or heading for assistive tech' land at three different levels of completeness, and the best implementation (reel) isn't the one used as the base for the library's own dialog primitive.
  - _Recommendation:_ Wire aria-labelledby/aria-describedby from q-dialog's rendered title/message ids onto its dialog container (mirroring the completeness of q-reel's lightbox aria-label), and give q-tooltip a real id-based aria-describedby link from the trigger to the bubble along with an aria-hidden that actually reflects visibility state.

#### q-icon — _fair_

Functionally clever (race-safe async icon loader with a sane fallback state machine) but it skips several house-style basics — no union-typed props, no test folder, and no accessibility attributes anywhere — plus it injects arbitrary remote SVG content via innerHTML with zero sanitization, which is a real risk for a shared, widely-consumed component.

  - _Why:_ tooltip.tsx:23 declares `@Prop() position: QTooltipPosition = 'top';` without reflect, then render() manually does `position={this.position}` on Host (tooltip.tsx:208) so the `:host([position="top"])` CSS selectors work. dialog.tsx already shows the idiomatic way to do this for an analogous enum prop: `@Prop({ attribute: 'backdrop-effect', reflect: true }) backdropEffect`. - [x] **[cleanliness]** 🟢 SAFE `tooltip.css:60` — font-size uses an invented one-off value (0.725rem) instead of the existing --q-font-size-sm token (0.7rem).
  - _Why:_ global.css defines `--q-font-size-sm: 0.7rem` as the small-text token, and no other component appears to use 0.725rem. This is exactly the kind of hardcoded magic number the house rules ask CSS to avoid when a token already covers the case.
