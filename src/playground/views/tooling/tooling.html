Developer tooling

Release notes from your project

Generate a content-hashed release feed, keep application versions aligned, and stage reviewed images. Your application owns its routes, authentication, fictional demo data and viewer.

Initialize and preview

The initializer is currently local-only. Install the reviewed packed tooling candidate until the coordinated npm release is published.

bunx --no-install wq-changelog init
bun run changelog:preview

Use Bun 1.4.2 or later in an application with a stable package version and a declared @webquark/tooling or @webquark/core dependency. Open http://127.0.0.1:4173/changelog/. Init creates a config, empty Unreleased notes, required folders, generator, static viewer and package scripts. Add your actual bullets to CHANGELOG.md.

Feed output stays under ignored public/changelog/generated/; the separate browser URL module is public/changelog/feed-url.js. Use init --dry-run to inspect the setup. Existing scaffold paths or conflicting script names stop init before writes; it preserves other package fields and ignore entries. Existing changelog setups use the manual reference. The application controls static hosting and framework routing.

bun run changelog:generate defaults to production; a fresh starter has an empty production feed. Preview defaults to development and initially shows an empty Unreleased entry. Explicit ENVIRONMENT_TYPE=prod or prod-rehearsal excludes Unreleased even in preview. Init invents no released history and adds no capture configuration.

Choose an API entry for custom integration

// Direct tooling dependency
import { checkVersions, generateWhatsNew } from '@webquark/tooling/changelog';

// The installation umbrella forwards the same separate API

Browser components use @webquark/browser or @webquark/core/browser. All five packages share one version and release channel; Angular and React integrations are optional.

Start with text notes

Use init for automatic setup, or the installed tooling README's manual reference for custom paths and viewers. Every included dated release needs its matching folder, even when text only. Text and manual images need no metadata adapter.

The runnable browser example has a real generator, local server, source notes and a fictional manual SVG image. Run its generate.ts and serve.ts using Bun 1.4.2 or later, then open http://127.0.0.1:4173/. Generated artifacts stay under ignored dist/.

The fictional sample notes and sample feed JSON are static format references. The feed keeps { releases }, Added/Changed/Fixed/Removed summaries and a visuals array. Generation hashes the JSON and image bytes and writes feed-url.ts; the runnable example connects the returned feedUrl to browser code.

wq-changelog version check --config ./changelog.config.ts
wq-changelog notes --config ./changelog.config.ts --include-unreleased

The application serves the whole generated folder. The viewer fetches the feed, resolves image URLs relative to its URL, and safely renders notes as plain text with textContent. Browser code imports no runtime tooling. Optional ReleaseFeed TypeScript imports are type only. Version-only checks require no feed or capture setup. Production settings exclude Unreleased.

Capture setup stays with the application

  1. Register reviewed page profiles or custom scenarios and their required fictional seed facts.
  2. Supply an adapter for an explicitly owned local/demo environment, real authentication, allowed network operations and cleanup evidence.
  3. Install browser binaries explicitly, then stage selected jobs. Lossless WebP is the default; PNG requires an explicit format and matching extension.
  4. Inspect staged images and the report, then publish that reviewed run after provenance, bytes, presentation and cleanup are rechecked.
wq-changelog capture stage --config ./changelog.config.ts --scenario release-panel
wq-changelog capture publish <run-id> --config ./changelog.config.ts

Automated capture requires an application metadata adapter, staging path and reviewed capture adapter. Stage writes review artifacts; publishing a reviewed run saves those bytes into Unreleased images. Generate notes afterward. Preparing a release archives notes and synchronizes configured versions. Publishing npm packages and deploying an application remain separate actions.
